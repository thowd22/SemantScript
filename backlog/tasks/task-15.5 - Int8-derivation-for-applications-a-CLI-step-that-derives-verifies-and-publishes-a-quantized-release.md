## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
semantscript package (TASK-14.9) reports int8 quantization as a size lever that would bring the Express example's 653.6 MiB trained release to about 227.6 MiB, under Lambda's 250 MiB zip limit, but marks it 'a measurement only' because no command derives an int8 release for an application: the derivation exists only in benchmarks/refund/program/quantize_release.py (quantize_release_artifact, tolerance-gated verification of the quantized encoder chain against the float32 chain over the release's verification records; results in benchmarks/refund/data/release-int8-2026-09-24 and docs/scaling-results.md, where the measured int8 refund release changed 1 of 80 attested cases and 0.105% of decisions). Make it a first-class step: a CLI command (for example semantscript releases derive --int8 <release> or package --int8) that derives an int8 release from a passing release, verifies it on the quantized graph, publishes it as its own release with provenance (source manifest digest, quantization settings, tolerance, disagreement counts) and lets releases promote/rollback and the runtime treat it like any release. The trained Express release in the main checkout is available read-only for a real measurement; the fixture artifact (runtime/test/fixtures) is the CI evidence. No paid API calls are needed. Related pages: docs/deploy.md, docs/cli-reference.md (releases, package), examples/express-app/README.md size table.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
Findings: quantize_release_artifact (trainer/src/semantscript_trainer/quantization.py) already derives+gates an int8 release but only for single-function releases with exactly 4 resources; the Express release has 2 functions (5 resources, one adapter, one encoder) and depth-routed releases have several encoders. Manifest provenance today = onnx.quantization settings on the encoder (schema/runtime loader/Python validator); disagreement figures are not recorded. An application release's verification records live in the build cache: datasets/v1/**.json whose file SHA-256 equals trainingProvenance.datasetSha256 (gold cases = attested) plus the adversarial sidecar (pinned by applications/<app>/functions/<id>/function.json adversarialDatasetSha256, else the unique sidecar whose baseDataset.datasetSha256 matches), as cli/src/training-cache.ts already finds them. The runtime fixture encoder has no MatMul, so quantize_dynamic cannot quantize it.

1. Model/trainer: generalize quantize_release_artifact to multi-function artifacts (every float32 encoder resource quantized, other resources copied and digest-checked; per-record chain = function's encoderRef/model.encoderRef -> adapterRef -> its heads; decision = per-head argmax tuple; QuantizationRecord gains optional function_id, required when the release has >1 function; labels only where the head has a support list; ECE gate per function; report gains per-function figures). Single-function refund driver and existing tests unchanged.
2. Manifest provenance: optional onnx.quantization.verification block {recordsChecked, attestedRecords, decisionChanges, attestedDecisionChanges, decisionChangeRate, sourceEce/quantizedEce (worst function), recordSource digests, functions[...]} added additively to schemas/application-artifact.v1.schema.json, runtime/src/artifact-loader.ts + artifact-types.ts, and the Python validator (artifact.py _validate_onnx_precision); older int8 manifests without it stay valid. Tests in runtime/test/artifact-loader.test.mjs and trainer tests.
